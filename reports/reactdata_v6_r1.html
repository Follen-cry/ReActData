模块化 ReActData pipeline：端到端验证与三任务混合训练实验

仓库 Follen-cry/ReActData（模块化重构 a1ce1f3）clone 到 /scratch/network/ssd2/junlin/ReActData-mod。先用原 v5 协议做 GPU 冒烟，再改写为 v6：VBVR 三个任务（scale / move / 2d_geo）、每次训练 128 个 datapoint 只过 1 epoch、Builder Agent 6 轮，在 8 × A40 内完成。

结论

  • 可运行 修复 2 个重构引入的 bug 后，新版 modular pipeline 端到端跑通：v5 冒烟（P0→DONE，0.49 h）和 v6 正式 run r1（P0→DONE，2.98 h，0 次失败）。
  • 无提升 6 个 agent 候选中，"按编辑幅度选 clip"（c002 / c006）在单次筛选中 +0.05，但在 4 个配对 seed 上确认时 D = −0.038 / −0.020，两者的 CI 都覆盖 0，最终选回固定 baseline。改变任务配比（c001）为 −0.002。
  • 训练有效 128 行 × 1 epoch 的 baseline 在 test 上比未训练模型高 +0.071（95% CI [+0.052, +0.093]），提升来自 move（+0.121）和 scale（+0.073）；geo 的旋转完全没学到（+0.020，只来自形状保真）。
  • 主要问题 训练噪声很大：5 个 baseline replicate 的 dev sd = 0.043（均值 0.127 的 34%），来源是随 seed 出现的部分崩坏（生成时破坏 A–D 格）。在这个噪声水平下，单次筛选挑出的 +0.05 正好是 6 选 1 的赢家诅咒幅度。

1. 端到端验证与修复的 bug

验证顺序：CPU 测试（49 项单元测试、portable flow、Linux bwrap 沙箱、15 项 v3 flow 断言）→ v5 原协议 GPU 冒烟（真实 Sonnet agent）→ v6 冒烟 → v6 正式 run。

两处修复同时打在 pipeline/（v5）和 pipeline-v6/。修复后 pipeline/ 单元测试 50/50 通过，pipeline-v6/ 50/50 通过。

运行中观察到、尚未修复的问题

  • 启动时 GPU 空闲检查有竞态：只在 launch 时看 nvidia-smi，模型加载要 1–2 分钟。冒烟中两次被邻居的 26 GB 进程挤爆（OOM），我自己的校准任务和冒烟也撞过一次。目前只靠 1 次 infra retry 兜底。
  • Runner 代码错误被归为 infra_failed：NameError / TypeError 会被重试并算作候选失败，应单独归类为 runner bug 并停止 run。
  • 运行中改代码会混用新旧模块：gpu_probes 是惰性 import，一个 job 在补丁中途加载了新模块和旧 train_entry（作废的冒烟 smoke6 c002）。建议每个 job 启动时快照实现 hash 并在结束时校验。
  • 冒烟测不到 generate probe：smoke 只有 4 步，而 generate probe 要求 step ≥ 4。正式 run 中 agent 没有请求 generate probe，所以这条 GPU 路径在本次仍未被实际执行（代码与 dev eval 调用一致）。
  • 共享集群：18:31–19:36 其他用户占满 torrnode11–15 的全部 A40 组；torrnode5/7 是 24 GB 的 RTX 6000，放不下。我把 slot 池扩到 9 个 A40 组（仍最多 2 个并发 = 8 GPU），r1 先等了 21 分钟。

2. v6 实验设计

数据

  • 任务：shape_color_then_scale、shape_color_then_move（analogy-grid 规则打分）、2d_geometric_transformation（VBVR-CustomEval 规则打分，同 v0）。
  • 训练池 480 clip（每任务 160），inner probe 32；dev 150、test 150（每任务 50），分数为三任务均值的等权平均。
  • 来源：v4/v0 的冻结池 + move 训练集新抽样；dev 复用 v0/v1 dev；test 中 move/geo 复用 v1/v0 test（以前用过一次），scale 新抽 50。
  • 隔离：812 组端点 md5 无跨 split 重复，生成参数无重复。打分校验：GT 1.0（geo 0.997），原样拷贝输入得 0（geo 0.12）。

训练与搜索

  • 1 run = 128 行 = 8 step × 16 行，每个 clip 至多一次（1 epoch；checks 和训练中都强制检查）。只训 F0 → final，不用 context / 中间帧，文本固定为评测文本。
  • baseline c000：每任务 43/43/42 个随机 clip，打乱顺序。
  • Agent 能控制的：任务配比、任务内选哪些 clip（看 pool_view.json 中的描述和像素统计）、顺序、loss 反馈。
  • 流程（design v3）：5 个 baseline replicate → 6 轮串行 agent（Sonnet，同一 session）→ top-2 在 4 个配对 seed 上确认（Bonferroni z = 2.24）→ 3 个 formal seed 在 test 上评测。

选择依据：只选有可靠规则打分器的三个任务（shape_outline_then_move 的 GT 在 analogy-grid 打分器上得 0，所以排除）；geo 视频是 70 帧 / 15 fps，scale/move 是 60 帧 / 16 fps，统一中间帧语义的成本高，而 v1/v4/v5 都发现 context 帧和中间目标帧无益或有害，因此 v6 只研究"选哪些数据、怎样配比"。数据点取上限 128，让选择有意义（从 480 中选 27%）。

5. 后续改进方向

  1. 先降训练噪声，再做搜索。sd 0.043 来自随 seed 出现的部分崩坏。lr 2× 离崩坏线（5×）只有 2.5 倍余量，可以按 replicate 方差选 lr，例如比较 1×/w2 和 2×/w3 各 5 个 seed 的均值和崩坏率，而不是看单次 run。也可以考虑更小的每步 batch（例如 4 行 × 32 步，需要改 ROWS_PER_STEP 契约），用更多更小的更新降低单步冲击。
  2. 筛选阶段每个候选至少跑 2 个配对 seed。训练只要 40 s，成本在 dev 生成，所以可以用 75 item × 2 seed 或更少的 diffusion 步数做筛选，让 top-k 不再由单次运气决定。本次 c002/c006 的 +0.05 约等于 6 个候选中最大噪声的期望值（≈ 1.27 sd）。
  3. 把崩坏作为 run 级诊断。A–D 格被破坏的比例（context_damaged）能直接分辨"规则没学到"和"训练坏了"。可以把它写进 report 给 agent 看，也可以作为 job 的自动检查。
  4. Pipeline 工程：GPU 租约 / 锁文件（launch 后在模型加载完成前保持占用，并在共享 FS 上做跨 run 互斥）；把 Runner 代码异常归为 runner_bug 并停止 run；每个 job 快照实现 hash；冒烟时按比例缩小 probe 间隔，使 generate probe 也被执行；v3 最终报告加入逐任务 test 表；把 test_undefined_names 和 v6_probe_cand 的 GPU 检查纳入发布前清单。
  5. 研究问题本身：8 步学不到 geo 的旋转，所以三任务中只有两个任务对数据选择敏感。可以做预算扫描（16 / 64 / 128 行，或允许 2–4 epoch），找到选择开始起作用的区间。Agent 6 轮都是 static 程序，还会把各任务之间的噪声差异当成可加效应（c004），可以在 instructions 中要求至少有一轮测试顺序或反馈，并给出逐任务的噪声 sd。
